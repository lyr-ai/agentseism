# Stage C — simple rules against AgentSeism v1

2026-09-25. Regenerated under **spec revision 3**, which it motivated (§3). **No API calls, no runs.** All numbers come from
`analysis/ci_v1/baseline_challenge.py`, which is deterministic and runs in
under a minute. It reuses the verified engine from the OC study: gate 1
matched the product's bootstrap 300/300, and gate 2 is the product's
`capability.evaluate`.

The question: does v1's statistical machinery earn its complexity against
the simplest rules someone would write instead?

| rule | definition |
|---|---|
| R1 naive aggregate | `mean(cand) − mean(base) ≤ −0.10` |
| R2 simple per-task | some task with baseline ≥ 0.8 and drop ≥ 0.5, with no inference |
| R3 count heuristic | some task with baseline ≥ 7/8 and candidate ≤ 2/8 |
| v1 | gate 1 (bootstrap over tasks) **or** gate 2 (Fisher + Bonferroni), as frozen |

## Verdict

**Gate 1 earns its complexity. Revision-2 gate 2 did not, and the challenge
found why: a design flaw. Revision 3 fixes it, and gate 2 now earns its
complexity too, though at K = 7 the margin is modest.**

### 1. Stage A/B cannot tell the rules apart (C1)

All four rules PASS Stage A and flag Stage B. Two observed points
discriminate nothing, so the comparison is made on the simulation grid.

### 2. Against R1 and R2, v1 is a different and far less flaky operating point (C2, C3)

| unchanged candidate, n = 8 | R1 | R2 | v1 |
|---|---|---|---|
| all tasks 0.95 | 0.3–3.5% | 0.1–0.4% | ≤ 0.1% |
| Stage-A-like (one noisy task) | **1.0–9.1%** | **2.5–2.9%** | ≤ 0.3% |
| flaky agent, all 0.70 | **9–20%** | **12–20%** | 0.7–2.2% (rev 2: 3.5–5.6%) |

R1 and R2 buy their sensitivity with false blocks. R1 catches a broad −0.20
drop with probability 0.95 against v1's 0.46. But on a suite with one noisy
task it blocks an unchanged PR up to 9% of the time, and on a flaky agent up
to 20%. That is a flaky CI check. **This is the case for gate 1: a population
test that does not mistake one noisy task for a regression.**

### 3. Against R3, frozen gate 2 is *worse*. The cause is how K is counted (C4, C5)

At n = 8, R3 and gate 2 disagree on exactly one cell for K ≥ 4:
**7/8 → 2/8**. R3 blocks it and gate 2 does not. Otherwise they are the same
rule, and **R3 is gate 2's boundary written as a fixed table**.

On a flaky agent, though, frozen gate 2 blocks more often than R3 (3.3–3.8%
against 1.4–2.7%). The reason is that the frozen spec divides α by the number
of **eligible** tasks. When the agent is flaky only 1–2 of 7 tasks are
eligible, so α/K relaxes and the gate loosens exactly where noise is highest.
Eligibility is decided on the same baseline, so the family the correction is
meant to control shrinks with the noise.

**With K = the declared suite size**, fixed before any run and not
data-dependent, the flaky-null false block drops to **0.4–0.6%**, below R3
everywhere. Power on a reliable suite is unchanged, because eligible ≈ suite
there (C5).

### 4. Gate 2's real advantage is scale (C6)

R3 has no multiplicity control, so its family-wise false-block rate grows
with the suite. On a flaky agent (p = 0.7) it is **1.4% at 5 tasks, 5.6% at
20 and 13.4% at 50**. Gate 2 with K = suite size stays **≤ 0.7%** at every
size. The price is per-task power, which falls from 0.87 (K = 5) to 0.66
(K ≥ 20), where R3 holds 0.91. That is the textbook multiplicity trade-off,
now with numbers on it.

## What this means for the decision

At the confirmatory design point (K = 7, n = 8), suite-K gate 2 against R3 is
a modest difference:

| | suite-K gate 2 | R3 |
|---|---|---|
| flaky-null false block | 0.6% | 2.0% |
| power, one task → 0.10 | 0.87 | 0.91 |

The machinery's value is that its false-block rate **does not grow** as a
team adds tasks, and that its boundary is derived rather than hand-picked.
It is not a large win at seven tasks.

**Adopted as spec revision 3** (see the design doc). After the rerun, at
n = 8:
- gate 2 alone false-blocks 0.4–0.8% on a flaky agent, below R3's 1.8–2.8% at
  every K;
- v1 as a whole is 0.7–2.2% there. At K = 5 it is marginally above R3 (2.2%
  vs 1.8%), because v1 also carries gate 1 (1.7%), which R3 does not have;
- detection at the design point is unchanged: one task → 0.10 is caught at
  0.87, and → 0.25 at 0.55.

Tables C1–C4 and C6 now use suite-K. C5 keeps both columns as the record of
the comparison that motivated the revision.
