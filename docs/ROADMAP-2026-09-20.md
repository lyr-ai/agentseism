## Phase 0 — re-freeze the research boundary

> AgentSeism is an **outcome-grounded regression testing and diagnosis
> framework for stochastic agents.**

Three principles:

1. A **user contract** defines which changes affect a release.
2. **Standard features** give cross-agent statistical measurement.
3. **Outcomes gate; traces diagnose.** Incomparable runs get no regression
   verdict.

**Explicitly not claimed as contributions:**

- general mutation testing;
- SPRT / adaptive sampling as such;
- `PASS` / `FAIL` / `INCONCLUSIVE` as such;
- behavioural fingerprint shift detection;
- a single composite agent score.

C2-H sealed — implementation kept, no GPU.

**Done when** the difference from AgentAssay fits in one sentence that does not
rely on "we implemented it better."

## Phase 1 — freeze the standard feature taxonomy

**Primary**

| Feature | Statistical unit | Metric |
|---|---|---|
| Task success | per independent run | success-rate difference |
| Recovery success | per run that hit a predefined error | conditional recovery rate |
| Efficiency to success | per successful run | steps, cost, latency per success |

**Diagnostic**

| Feature | Use |
|---|---|
| Tool-error profile | timeout, schema error, non-zero exit |
| Progress profile | first effective edit, first test, submission point |
| Trace divergence | localisation only; never blocks a merge on its own |

Also fixed: effect size, confidence interval, independent unit, handling of
missing or invalid runs, minimum practically important difference,
scenario-level aggregation, multiple-testing policy.

**Done when** every feature is computable by deterministic code from traces and
outcomes, **with no free-text LLM judge**.

> That last clause is the Phase 2 `reason` lesson in the other project, stated
> as an entry condition rather than learned again: a field that only a judge
> can evaluate cannot be a gate, and a field with no contract ends up carrying
> weight it was never given.

## Phase 2 — the feature contract

Built-in defaults, user-overridable.

```yaml
features:
  task_success:
    evaluator: swebench_resolved
    regression_threshold: -0.10
    gate: true
  recovery_success:
    condition: malformed_tool_call_observed
    regression_threshold: -0.15
    gate: true
  cost_per_success:
    regression_threshold: 0.25
    gate: warning

comparability:
  require_same:
    - model_revision
    - serving_runtime
    - prompt_version
    - scaffold_version
```

Four states: `PASS`, `REGRESSION`, `INSUFFICIENT_EVIDENCE`, `INCOMPARABLE`.

**Done when** one contract drives the experiment, the CI verdict and the report
— so a metric cannot be chosen after the analysis.

## Phase 3 — the minimal mutation suite

Mutations are the instrument, not the contribution. Three in the first round:

| Mutation | Primary feature | Expected direction | Negative control |
|---|---|---|---|
| reduce max steps | task success | down | early tool validity should not fall noticeably |
| remove the error-recovery hint | recovery success | down | runs that hit no error should be unchanged |
| prune context earlier | long-task success | down | short-task success should be unchanged |

**Deferred, with reasons:**

| Deferred | Why |
|---|---|
| model swap | confounds with comparability |
| tool noise | too close to AgentNoiseBench |
| random prompt noise | not an engineering change |
| tool timeout | **real wall clock is unstable**; better as its own later study |

> The tool-timeout deferral is a correction to the earlier matrix, and a
> correct one. A mutation whose effect is measured through wall clock inherits
> the variance of the machine it runs on; the donor data spans 258 s to 3107 s
> on identical configuration. It would have been the hardest of the four to
> read and was registered as if it were the easiest.

**Frozen per mutation, before the first run:**

```
causal hypothesis
primary feature
negative control
effect threshold
trial allocation
stopping rule
failure interpretation
```

**Done when** the result answers the pre-registered question whether it comes
out positive or negative. *Failure interpretation* is the item that makes that
true: without it, a null result has nowhere to go except "inconclusive, try
more trials".

## Phase 4 — offline counterexamples on frozen data — **ALREADY DONE**

Completed at `af9bc4e`, `paper/COMPARABILITY_COUNTEREXAMPLES.md`. No machine,
no model, recomputed from committed artifacts.

**One correction to the premise as stated.** Analysis A was specified as "five
runs, all resolved". They were not: **four of the five resolved.** `r4`'s patch
did not fix the issue (`paper/manifests/correctness_labels.json`). The
counterexample is built on the four correct runs and is therefore **six
pairs, not ten**.

The correction makes the case two-sided and stronger. Four accepted solutions,
no two alike — a trajectory-identity check blocks all four. And one run of five
genuinely was wrong — so the variation is not uniformly benign either. Only the
outcome separates those two, which is the gate-on-outcomes argument from both
directions instead of one.

### Analysis A — harmless trajectory variation

Four runs, one task, all resolved. Six correct/correct pairs, zero regressions
in ground truth:

| Signal | Fires | False-positive rate |
|---|---:|---:|
| tool mix differs | 6/6 | **100%** |
| final patch size > 20% | 5/6 | 83% |
| wall clock > 50% | 5/6 | 83% |
| trace length > 20% | 3/6 | 50% |
| **any of three** | **6/6** | **100%** |

An outcome-first gate passes all six correctly.

### Analysis B — an incomparable serving stack

Gate 9, agent held fixed, only A100 → H100 and a driver version:

```
raw response identical    0 / 23
structured action equal   0 / 23
```

A trace detector reports behavioural change on 23/23. Correct output:

```
INCOMPARABLE
reason: serving fingerprint changed
```

not

```
REGRESSION
reason: behavioral fingerprint shifted
```

**Both completion criteria met**, and the document states its limits — one
task, illustrative thresholds, a single stack pair, descriptive rather than
causal. The paper route is not paused.

## Phase 5 — the minimal vertical slice

One end-to-end path:

```
load contract → check comparability → run baseline and candidate
  → feature scorecard → outcome verdict → trace RCA for regressions
  → PR report
```

**In:** YAML feature contract, normalized trace schema, cached baseline,
repeated candidate execution, feature scorecard, four-state verdict, serving
fingerprint, one simple RCA (the first stage associated with the outcome
regression), Markdown/JSON PR report.

**Out:** dashboard, multi-framework adapters, composite scoring, causal graphs,
LLM explanation, adaptive-sampling optimisation.

**Done when** a developer who has never seen the project can answer, from the
PR report alone: what broke, how strong the evidence is, and whether to block
the merge.

## Phase 6 — a low-cost pilot

1 public coding agent · 3 tasks · 3 mutations · 3 trials per cell · cached
baseline · **hard budget $20–30**.

Answers only: can features be extracted stably; does each mutation move its
registered feature; do the negative controls hold; do the outcome gate and the
trace detector disagree; is the RCA report intelligible.

**No formal statistical verdict, and three repetitions are not dressed up as
adequate power.**

Continue gate — all five:

- at least two mutations hit their registered feature;
- harmless variation does not block a merge;
- a serving mismatch is judged incomparable;
- the RCA points at the right component or stage at least once;
- the report needs no lengthy explanation.

**If it fails, change the features or the contract — not the trial count.**
More trials on a metric that does not separate buys precision about the wrong
thing.

## Phase 7 — pre-registration and the paper experiment

Only after the pilot passes.

- **RQ1** do engineering mutations produce the pre-registered feature-specific
  signatures?
- **RQ2** does outcome-first gating raise fewer alarms on harmless variation
  than trace-only detection?
- **RQ3** does the scorecard localise a fault more specifically than task
  success alone?
- **RQ4** does the comparability gate stop serving-stack drift being
  attributed to an agent revision?

Minimum shape: 1–2 public agents, 5–8 tasks, 3 mutations, around 5 repetitions
with the number set by pilot variance, scenario-level paired analysis, effect
sizes and CIs and effective independent N, exploratory and confirmatory
analyses kept apart.

**No promise of fewer samples or higher power** unless the experiment supports
it.

## Phase 8 — product validation

Parallel to the paper, not merged with it. 3–5 potential users review a PR
report; no install required. Which conclusion is credible, which metric is
useless, when would they block a merge, is `INCOMPARABLE` understandable, does
the RCA save time reading traces.

Routes that avoid cold calls: a GitHub demo, a web page that turns an uploaded
trace into a report, a concrete case posted publicly, anonymous contract or
report submission, one non-invasive demo PR against a public agent repository.
